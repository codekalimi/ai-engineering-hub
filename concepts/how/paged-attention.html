How does PagedAttention work?

In one lineThe KV cache is stored in small fixed-size blocks, like operating-system memory pages, allocated only as a sequence grows, so almost no memory is wasted.

Step by step
  1. Older servers reserved one contiguous memory region per request, sized for the maximum possible length.
  2. Most of that reserved memory was never used, and the gaps fragmented memory.
  3. PagedAttention splits each sequence's KV cache into fixed-size blocks that can sit anywhere in memory.
  4. A block table maps each sequence's logical blocks to physical blocks, and new blocks are allocated only when needed.
  5. Requests with the same prefix can point to the same physical blocks.
Key details
  • Near-zero waste means bigger batches and higher throughput on the same GPU.
  • It's the core idea behind vLLM.

Use it

What you'd write at work

You don't call PagedAttention; you size it. These vLLM settings decide how much GPU memory becomes KV-cache blocks and whether prefixes are shared.

python
from vllm import LLM

llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct",
    gpu_memory_utilization=0.90,     # weights + activations first; the rest becomes KV-cache blocks
    max_model_len=8192,              # longest sequence one request may reach
    block_size=16,                   # tokens per KV block (a "page")
    enable_prefix_caching=True,      # requests with the same prefix share blocks
)
# The startup log reports the resulting KV-cache size in tokens and the maximum concurrency.

Checked, not run: needs NVIDIA GPUs and vLLM, which can't be installed on the test machine (a Mac): syntax checked only.

Under the hood

What the library does for you, with its real classes

What the paged kernel does, in PyTorch: KV vectors live in a pool of fixed-size blocks anywhere in memory; a block table says which blocks belong to a sequence; attention gathers through it. The result equals ordinary attention.

python
import torch
import torch.nn.functional as F

torch.manual_seed(0)
block_size, num_blocks, heads, dim = 4, 16, 2, 8
k_pool = torch.zeros(num_blocks, block_size, heads, dim)     # Step 3: one big pool of blocks
v_pool = torch.zeros(num_blocks, block_size, heads, dim)
free = list(range(num_blocks))[::-1]
block_table = {}                                             # Step 4: sequence -> its physical blocks

def append(seq, k, v, pos):
    if pos % block_size == 0:                                # new block only when the last is full
        block_table.setdefault(seq, []).append(free.pop())
    b = block_table[seq][pos // block_size]
    k_pool[b, pos % block_size], v_pool[b, pos % block_size] = k, v

seq_len = 10
K, V = torch.randn(seq_len, heads, dim), torch.randn(seq_len, heads, dim)
for pos in range(seq_len):
    append("req-A", K[pos], V[pos], pos)
print("req-A block table:", block_table["req-A"], f"({seq_len} tokens in {len(block_table['req-A'])} blocks)")

# attention for the newest query, gathering K/V through the block table
q = torch.randn(heads, dim)
blocks = block_table["req-A"]
k_seq = k_pool[blocks].reshape(-1, heads, dim)[:seq_len]
v_seq = v_pool[blocks].reshape(-1, heads, dim)[:seq_len]
paged = F.scaled_dot_product_attention(q[:, None], k_seq.transpose(0, 1), v_seq.transpose(0, 1))
dense = F.scaled_dot_product_attention(q[:, None], K.transpose(0, 1), V.transpose(0, 1))
print("paged result equals contiguous attention:", torch.allclose(paged, dense, atol=1e-6))

block_table["req-B"] = blocks[:2]                            # Step 5: same prefix -> share blocks, no copy
print("req-B shares blocks", block_table["req-B"], "with req-A")

✓ Ran with torch 2.15.0.

What it printed
req-A block table: [0, 1, 2] (10 tokens in 3 blocks)
paged result equals contiguous attention: True
req-B shares blocks [0, 1] with req-A

From scratch

The idea in plain Python, no libraries

A tiny version of the mechanism. The Step comments match the numbered steps above. Save it as a .py file and run python3 file.py: nothing to install.

python3 · standard library only
# KV cache in fixed-size blocks that can sit anywhere in GPU memory, plus a block table per sequence.
BLOCK = 4                                        # tokens per block
free_blocks = list(range(10))                    # physical blocks on the GPU
tables, lengths, refcount = {}, {}, {}

def append_token(seq):
    # Step 3-4: a new block is allocated only when the sequence's last block is full
    if lengths.get(seq, 0) % BLOCK == 0:
        block = free_blocks.pop(0)
        tables.setdefault(seq, []).append(block)
        refcount[block] = 1
    lengths[seq] = lengths.get(seq, 0) + 1

def fork(parent, child):
    # Step 5: a request with the same prefix points at the SAME physical blocks
    # (copy-on-write: a shared block is copied only when one of them writes to it)
    tables[child], lengths[child] = list(tables[parent]), lengths[parent]
    for block in tables[child]:
        refcount[block] += 1

for _ in range(6):
    append_token("req1")                         # 6 tokens -> 2 blocks
for _ in range(3):
    append_token("req2")                         # 3 tokens -> 1 block
fork("req1", "req1-sample2")                     # e.g. a second sample of the same prompt

print("block tables (logical -> physical):", tables)
print("blocks shared by more than one sequence:", [b for b, n in refcount.items() if n > 1])
used = lengths["req1"] + lengths["req2"]
print(f"paged: {len(tables['req1']) + len(tables['req2'])} blocks = {(len(tables['req1']) + len(tables['req2'])) * BLOCK} slots for {used} tokens")
# Step 1-2: the old way reserved the maximum length for every request up front
print(f"old way: 2 requests x 2048 max tokens = 4096 slots reserved for {used} tokens")

✓ Ran with plain Python 3.9+.

What it prints
block tables (logical -> physical): {'req1': [0, 1], 'req2': [2], 'req1-sample2': [0, 1]}
blocks shared by more than one sequence: [0, 1]
paged: 3 blocks = 12 slots for 9 tokens
old way: 2 requests x 2048 max tokens = 4096 slots reserved for 9 tokens
Watch it in a real system
  • vLLM’s startup log reports the KV-cache size it allocated (as tokens/blocks); change --gpu-memory-utilization or --max-model-len and see it change.
  • Read vllm/core/block_manager (older versions) or the KV-cache manager in the v1 engine: block tables like the one below, mapping each sequence to physical blocks.
  • Turn prefix caching on (--enable-prefix-caching, the default in recent versions) and send many requests with the same long system prompt: KV-cache usage grows far less than the request count.
