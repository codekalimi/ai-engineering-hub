How does the KV cache work?

In one lineKeys and values for tokens already processed are stored, so each new token only computes its own and reads the rest from the cache.

Step by step
  1. During prefill, the whole prompt is processed in parallel, and every token's keys and values are saved in GPU memory.
  2. During decode, each new token computes only its own query, key and value.
  3. Its query attends over the cached keys and values instead of recomputing the whole prefix.
  4. Its own key and value are appended, so the cache grows by one token per step.
Key details
  • Size ≈ 2 × layers × KV heads × head dim × bytes × tokens: about 0.3 MB per token for a 70B GQA model in FP16.
  • The cache, not the weights, usually limits how many requests fit on a GPU at once.
  • Prompt (prefix) caching reuses the cached keys and values of an identical prefix across requests.

Use it

What you'd write at work

The cache is on by default; you mostly feel it as speed. Here a real 0.5B model generates the same 30 tokens with and without it.

python
import time
from transformers import AutoModelForCausalLM, AutoTokenizer

name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)
inputs = tok("Write a short poem about the sea.", return_tensors="pt")

for use_cache in (True, False):
    start = time.time()
    model.generate(**inputs, max_new_tokens=30, do_sample=False, use_cache=use_cache)
    print(f"use_cache={use_cache}: {time.time() - start:.1f}s")

✓ Ran with transformers 5.24.0.

What it printed
use_cache=True: 0.6s
use_cache=False: 3.9s

Under the hood

What the library does for you, with its real classes

Looking inside the cache object the model fills: one key and value tensor per layer, growing by one position per generated token.

python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, DynamicCache

name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name).eval()
ids = tok("The capital of France is", return_tensors="pt").input_ids

cache = DynamicCache()
with torch.no_grad():
    out = model(input_ids=ids, cache=cache, use_cache=True)      # Step 1: prefill the whole prompt
    print("after prefill:", cache.get_seq_length(), "tokens cached in", len(cache.layers), "layers")
    print("layer 0 keys [batch, kv_heads, tokens, head_dim]:", tuple(cache.layers[0].keys.shape))
    for _ in range(3):
        nxt = out.logits[:, -1:].argmax(-1)                      # Step 2: only the newest token goes in
        out = model(input_ids=nxt, cache=cache, use_cache=True)  # Step 3: it attends over the cache
        print(f"decode {tok.decode(nxt[0])!r:9} input length {nxt.shape[1]} -> cache {cache.get_seq_length()}")  # Step 4

cfg = model.config
head_dim = cfg.hidden_size // cfg.num_attention_heads
per_token = 2 * cfg.num_hidden_layers * cfg.num_key_value_heads * head_dim * 2   # K+V, 2 bytes each
print(f"{per_token / 1024:.0f} KB per token -> {per_token * 32768 / 1e9:.2f} GB for one 32k-token context")

✓ Ran with torch 2.15.0, transformers 5.24.0.

From scratch

The idea in plain Python, no libraries

A tiny version of the mechanism. The Step comments match the numbered steps above. Save it as a .py file and run python3 file.py: nothing to install.

python3 · standard library only
# Count the work with and without a KV cache. "Work" = how many tokens get K and V computed.
prompt = ["The", "capital", "of", "France", "is"]
new_tokens = ["Paris", ",", "a", "city"]

def kv(token):                    # stands in for: token vector x weight matrices W_k and W_v
    return (f"K({token})", f"V({token})")

# Without a cache: every step recomputes K and V for the whole sequence
work_no_cache, seq = 0, list(prompt)
for tok in new_tokens:
    work_no_cache += len(seq)
    seq.append(tok)

# Step 1 (prefill): the whole prompt at once, saved in the cache
cache = [kv(t) for t in prompt]
work_cache = len(prompt)
print(f"prefill: cached {len(cache)} tokens")
for tok in new_tokens:
    # Step 2: the newest token computes only its own K and V
    k, v = kv(tok)
    work_cache += 1
    # Step 3: its query attends over the cached K/V (read, not recomputed)
    # Step 4: append, so the cache grows by one token per step
    cache.append((k, v))
    print(f"decode {tok!r:8} reads {len(cache) - 1} cached K/V, computes 1, cache now {len(cache)}")
print(f"K/V computations without cache: {work_no_cache}, with cache: {work_cache}")

# Memory per token = 2 (K and V) x layers x KV heads x head size x bytes
layers, kv_heads, head_dim, fp16 = 80, 8, 128, 2
per_token = 2 * layers * kv_heads * head_dim * fp16
print(f"70B-style model: {per_token / 1e6:.2f} MB per token, {per_token * 8192 / 1e9:.1f} GB for one 8k context")

✓ Ran with plain Python 3.9+.

What it prints

decode ','      reads 6 cached K/V, computes 1, cache now 7
decode 'a'      reads 7 cached K/V, computes 1, cache now 8
decode 'city'   reads 8 cached K/V, computes 1, cache now 9
K/V computations without cache: 26, with cache: 9
70B-style model: 0.33 MB per token, 2.7 GB for one 8k context
Watch it in a real system
  • Hugging Face: out = model(**inputs, use_cache=True) returns out.past_key_values; pass it back with the next token to skip recomputing the prefix.
  • Time model.generate(..., use_cache=False) against the default: generation gets much slower as the output grows.
  • vLLM prints the KV-cache size (in tokens) at startup and exposes KV-cache usage on its /metrics endpoint.
