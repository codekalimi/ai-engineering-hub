How does an agent act on behalf of a user safely (delegated OAuth)?

In one lineThe user grants the app limited, scoped access through OAuth, and the agent calls APIs with that user's token, so it can never see or do more than the user could.

Step by step
  1. The user signs in and approves specific scopes, like reading their calendar.
  2. The identity provider issues a scoped, short-lived access token for that user.
  3. The agent runs with that token rather than a powerful service account.
  4. The target API enforces the user's own permissions on every call.
Key details
  • This contains the damage from prompt injection: the agent can't exceed the user's access.
  • Request the narrowest scopes needed, and keep write scopes behind approval.
  • Log every action with the user's identity for audit.

Use it

What you'd write at work

The user's token travels in the runtime context. The model never sees it (it isn't a tool argument); the tool passes it to the API.

python
from dataclasses import dataclass
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model
from langchain.tools import ToolRuntime, tool

@dataclass
class UserContext:
    user_id: str
    access_token: str            # issued by your identity provider after the user consented

def calendar_api(token, day):    # stands in for the real API, which checks the token itself
    events = {"meera": ["10:00 design review", "13:00 lunch with Arjun"]}
    return events.get(TOKENS.get(token, ""), "401 unauthorized")
TOKENS = {"tok-meera-read": "meera"}

@tool
def read_calendar(day: str, runtime: ToolRuntime[UserContext]) -> str:
    """Read the signed-in user's calendar for a day."""
    return str(calendar_api(runtime.context.access_token, day))   # the USER's token, not a service account

print("what the model sees of the tool:", read_calendar.args)     # no token in here
agent = create_agent(init_chat_model("anthropic:claude-opus-5-5"), [read_calendar], context_schema=UserContext)
result = agent.invoke({"messages": [("user", "What's on my calendar today?")]},
                      context=UserContext(user_id="meera", access_token="tok-meera-read"))
print(result["messages"][-1].content)

✓ Ran with langchain 1.5.2 · with a scripted chat model in place of the API.

What it printed
what the model sees of the tool: {'day': {'title': 'Day', 'type': 'string'}}
You have a design review at 10:00 and lunch with Arjun at 13:00.

Under the hood

What the library does for you, with its real classes

What an auth library and the API do with that token: a token exchange for a narrow, short-lived token, then checks of audience, expiry and scope. The identity provider is mocked; the request shape is the standard OAuth token exchange (RFC 8693).

python
import base64
import json
import time
import httpx

def fake_idp(request):                     # stands in for your identity provider's /token endpoint
    form = dict(x.split("=") for x in request.content.decode().split("&"))
    claims = {"sub": "meera", "aud": form["audience"], "scope": form["scope"].replace("+", " "), "exp": int(time.time()) + 300}
    payload = base64.urlsafe_b64encode(json.dumps(claims).encode()).decode().rstrip("=")
    return httpx.Response(200, json={"access_token": f"header.{payload}.signature", "expires_in": 300})

idp = httpx.Client(transport=httpx.MockTransport(fake_idp))
# Steps 1-2: swap the user's login token for a narrow token for ONE API
resp = idp.post("https://idp.example.com/oauth/token", data={
    "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
    "subject_token": "<the user's token>",
    "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
    "audience": "calendar-api",
    "scope": "calendar.read",
})
token = resp.json()["access_token"]

# Step 4: what the API checks on every call (after verifying the signature)
part = token.split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(part + "=" * (-len(part) % 4)))
print("claims:", {k: claims[k] for k in ("sub", "aud", "scope")}, f"expires in {claims['exp'] - int(time.time())}s")
for needed in ("calendar.read", "calendar.write"):
    ok = claims["aud"] == "calendar-api" and claims["exp"] > time.time() and needed in claims["scope"].split()
    print(f"{needed}: {'allowed' if ok else '403 forbidden'}")

✓ Ran with Python 3.12.14.

What it printed
claims: {'sub': 'meera', 'aud': 'calendar-api', 'scope': 'calendar.read'} expires in 300s
calendar.read: allowed
calendar.write: 403 forbidden

From scratch

The idea in plain Python, no libraries

A tiny version of the mechanism. The Step comments match the numbered steps above. Save it as a .py file and run python3 file.py: nothing to install.

python3 · standard library only
# Delegated access, simplified: real tokens are JWTs signed with RSA/EC keys by an identity provider.
import base64, hashlib, hmac, json, time

IDP_KEY = b"identity-provider-secret"              # shared by the identity provider and the API

def b64(data): return base64.urlsafe_b64encode(json.dumps(data).encode()).decode().rstrip("=")
def unb64(s): return json.loads(base64.urlsafe_b64decode(s + "=" * (-len(s) % 4)))
def sign(body): return hmac.new(IDP_KEY, body.encode(), hashlib.sha256).hexdigest()[:16]

def issue_token(user, scopes, ttl=600):
    # Step 1-2: the user signs in and approves scopes; the IdP issues a short-lived token
    body = b64({"sub": user, "scope": " ".join(scopes), "aud": "calendar-api", "exp": int(time.time()) + ttl})
    return body + "." + sign(body)

def calendar_api(token, action, owner):
    # Step 4: the API checks signature, audience, expiry, scope AND the user's own permissions
    body, sig = token.split(".")
    if not hmac.compare_digest(sig, sign(body)):
        return "401 bad signature"
    claims = unb64(body)
    if claims["aud"] != "calendar-api" or claims["exp"] < time.time():
        return "401 wrong audience or expired"
    need = "calendar.read" if action == "read" else "calendar.write"
    if need not in claims["scope"].split():
        return f"403 token lacks scope {need}"
    if owner != claims["sub"]:
        return f"403 {claims['sub']} cannot access {owner}'s calendar"
    return f"200 {action} {owner}'s calendar"

token = issue_token("meera", ["calendar.read"])
claims = unb64(token.split(".")[0])
print("token says:", {k: claims[k] for k in ("sub", "aud", "scope")}, "+ an expiry 10 minutes away")
# Step 3: the agent acts with the USER's token, never with a powerful service account
for action, owner in [("read", "meera"), ("write", "meera"), ("read", "ceo")]:
    print(f"agent tries to {action} {owner}'s calendar: {calendar_api(token, action, owner)}")

✓ Ran with plain Python 3.9+.

What it prints
token says: {'sub': 'meera', 'aud': 'calendar-api', 'scope': 'calendar.read'} + an expiry 10 minutes away
agent tries to read meera's calendar: 200 read meera's calendar
agent tries to write meera's calendar: 403 token lacks scope calendar.write
agent tries to read ceo's calendar: 403 meera cannot access ceo's calendar
Watch it in a real system
  • Decode a token locally to read its claims (sub, aud, scope, exp): the payload is the middle part, base64url-encoded. Don’t paste real tokens into websites.
  • Call the target API with a token that lacks a scope and confirm you get a 403: that is the API enforcing the user’s permissions, not your agent.
  • Log which user and which scopes every agent tool call ran with; that audit trail is what security reviewers ask for.
