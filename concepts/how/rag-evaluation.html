How do you measure RAG quality (retrieval vs generation)?

In one lineScore the two halves separately: did retrieval find the right chunks, and is the answer faithful to those chunks, relevant to the question and correct?

Step by step
  1. For each test question, record which chunks (or documents) contain the answer.
  2. Retrieval metrics: recall@k (was a correct chunk in the top k?) and MRR (how high it ranked).
  3. Faithfulness: is every claim in the answer supported by the retrieved context?
  4. Answer relevance: does it actually address the question?
  5. Correctness: does it match the reference answer?
Key details
  • Low recall → fix retrieval (chunking, hybrid search, reranking). Low faithfulness with good recall → fix the prompt or model.
  • Libraries such as Ragas and LangSmith evaluators implement these metrics.

Use it

What you'd write at work

Score the retriever on its own with labelled questions: recall@k and MRR. Real retriever and real (local) embeddings.

python
from langchain.embeddings import init_embeddings
from langchain_core.vectorstores import InMemoryVectorStore

chunks = {"c1": "Refunds are accepted within 30 days of purchase.",
          "c2": "Shipping takes 3 to 5 working days.",
          "c3": "Our warranty covers manufacturing defects for 2 years.",
          "c4": "Support is open 9am to 5pm on weekdays."}
store = InMemoryVectorStore(init_embeddings("openai:text-embedding-3-small"))
store.add_texts(list(chunks.values()), ids=list(chunks))

labelled = [("How long do I have to return something?", "c1"),      # Step 1: question -> right chunk
            ("How long is the warranty?", "c3"),
            ("When can I call support?", "c4"),
            ("Is a broken screen covered?", "c3")]
k, hits, rr = 2, 0, 0.0
for question, right in labelled:
    ranked = [d.id for d in store.similarity_search(question, k=k)]
    hits += right in ranked                                           # Step 2: recall@k
    rr += 1 / (ranked.index(right) + 1) if right in ranked else 0     #         and MRR
    print(f"{question!r:44} -> {ranked} {'ok' if right in ranked else 'MISS'}")
print(f"recall@{k} = {hits}/{len(labelled)}, MRR = {rr / len(labelled):.2f}")

✓ Ran with langchain 1.5.2, langchain-core 1.8.4 · with a local embedding model (all-MiniLM-L6-v2) in place of the embedding API.

What it printed
'How long do I have to return something?'    -> ['c1', 'c2'] ok
'How long is the warranty?'                  -> ['c3', 'c2'] ok
'When can I call support?'                   -> ['c4', 'c2'] ok
'Is a broken screen covered?'                -> ['c3', 'c4'] ok
recall@2 = 4/4, MRR = 1.00

Under the hood

What the library does for you, with its real classes

How a faithfulness metric (as in Ragas) works: one LLM call splits the answer into claims, another checks each claim against the context; the score is the supported fraction.

python
from pydantic import BaseModel
from langchain.chat_models import init_chat_model

class Claims(BaseModel):
    claims: list[str]

class Verdict(BaseModel):
    supported: bool

judge = init_chat_model("anthropic:claude-sonnet-5-5")
context = "Support is open 9am to 5pm on weekdays."
answer = "Support is open 9am to 5pm, including weekends."

claims = judge.with_structured_output(Claims).invoke(f"Split into atomic factual claims:\n{answer}").claims
verdicts = [judge.with_structured_output(Verdict).invoke(f"Context: {context}\nIs this claim supported? {c}").supported
            for c in claims]                                       # Step 3: one check per claim
for c, v in zip(claims, verdicts):
    print(f"{'supported  ' if v else 'UNSUPPORTED'} {c}")
print(f"faithfulness = {sum(verdicts)}/{len(verdicts)} = {sum(verdicts) / len(verdicts):.2f}")

✓ Ran with langchain 1.5.2 · with a scripted chat model in place of the API.

What it printed
supported   Support is open 9am to 5pm.
UNSUPPORTED Support is open on weekends.
faithfulness = 1/2 = 0.50

From scratch

The idea in plain Python, no libraries

A tiny version of the mechanism. The Step comments match the numbered steps above. Save it as a .py file and run python3 file.py: nothing to install.

python3 · standard library only
# Step 1: for each test question, which chunk ids contain the answer
tests = [
    {"q": "refund window", "relevant": {"c7"}, "retrieved": ["c2", "c7", "c9"],
     "context": "refunds within 30 days", "answer": "30 days", "reference": "30 days"},
    {"q": "warranty length", "relevant": {"c4"}, "retrieved": ["c1", "c3", "c8"],
     "context": "shipping takes 3 days", "answer": "1 year", "reference": "2 years"},
    {"q": "support hours", "relevant": {"c5"}, "retrieved": ["c5", "c6", "c2"],
     "context": "support 9am to 5pm weekdays", "answer": "9am to 5pm, also weekends", "reference": "9am to 5pm"},
]
k = 3
for t in tests:
    # Step 2: retrieval metrics - was a right chunk in the top k, and how high?
    rank = next((i + 1 for i, c in enumerate(t["retrieved"][:k]) if c in t["relevant"]), None)
    t["recall"], t["rr"] = rank is not None, (1 / rank if rank else 0.0)
    # Step 3: faithfulness - is every claim in the context? (an LLM judge in real life)
    claims = [c.strip().replace("also ", "") for c in t["answer"].split(",")]
    t["faithful"] = all(c in t["context"] for c in claims)
    # Step 5: correctness against the reference answer (Step 4, relevance, is judged similarly)
    t["correct"] = t["answer"].startswith(t["reference"])
    print(f"{t['q']:16} recall@{k}={int(t['recall'])}  RR={t['rr']:.2f}  faithful={t['faithful']}  correct={t['correct']}")
n = len(tests)
print(f"recall@{k} = {sum(t['recall'] for t in tests)}/{n}, MRR = {sum(t['rr'] for t in tests) / n:.2f}")
print("diagnosis: 'warranty' failed at retrieval (fix search); 'support hours' retrieved well but")
print("           added an unsupported claim (fix the prompt or the model)")

✓ Ran with plain Python 3.9+.

What it prints

warranty length  recall@3=0  RR=0.00  faithful=False  correct=False
support hours    recall@3=1  RR=1.00  faithful=False  correct=True
recall@3 = 2/3, MRR = 0.50

           added an unsupported claim (fix the prompt or the model)
Watch it in a real system
  • Log the retrieved chunk ids for every test question; recall@k and MRR need nothing more than those ids and your labels.
  • Libraries such as Ragas, DeepEval and LangSmith evaluators provide faithfulness and relevance judges; read a sample of their verdicts before trusting the numbers.
  • For every failure, decide first: was the right chunk retrieved? That single question splits retrieval bugs from generation bugs.
