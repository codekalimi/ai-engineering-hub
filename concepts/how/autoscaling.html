How does autoscaling LLM inference work?

In one lineLoad metrics like queue depth or KV-cache usage trigger new replicas; if no GPU node is free, the node autoscaler adds one, and the replica takes traffic once the model is loaded.

Step by step
  1. The serving engine exports load metrics such as queue length and KV-cache utilization.
  2. An autoscaler watches them and adds replicas when they cross a threshold (CPU usage is useless here).
  3. If no GPU node has room, the node autoscaler provisions a new GPU machine.
  4. The new replica pulls the image and loads the weights.
  5. Once it passes readiness checks, it starts receiving traffic.
Key details
  • Scale-up is slow (minutes), so keep warm replicas or a capacity buffer.
  • Cache weights on local NVMe and pre-pull images to shorten cold starts.
  • GPU capacity can be scarce; reservations help for critical services.

Use it

What you'd write at work

Scale inference replicas on the serving engine's queue, not on CPU. A KEDA ScaledObject reading vLLM's Prometheus metric (YAML; the test parses it).

yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: vllm-chat
spec:
  scaleTargetRef:
    name: vllm-chat              # the Deployment running vLLM
  minReplicaCount: 1
  maxReplicaCount: 8
  cooldownPeriod: 300            # wait before scaling down: new GPU replicas are slow to start
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring:9090
        query: sum(vllm:num_requests_waiting{deployment="vllm-chat"})
        threshold: "5"           # target waiting requests per replica

Under the hood

What the library does for you, with its real classes

The decision rule the Kubernetes autoscaler applies (KEDA feeds it the metric): desired = ceil(current x metric / target), with a tolerance band and a slow scale-down window.

python
import math

TARGET, TOLERANCE, MIN, MAX = 5.0, 0.1, 1, 8
history = []                                       # recent recommendations, for the scale-down window

def desired_replicas(current, waiting_total):
    per_replica = waiting_total / current          # Step 1: the metric, averaged per replica
    ratio = per_replica / TARGET
    if abs(ratio - 1.0) <= TOLERANCE:              # inside the tolerance band: do nothing
        return current
    want = min(MAX, max(MIN, math.ceil(current * ratio)))   # Step 2: the HPA formula
    history.append(want)
    return max(history[-5:]) if want < current else want    # scale down only to the max of recent wishes

replicas = 1
for tick, waiting in enumerate([4, 12, 30, 45, 40, 20, 6, 2, 0, 0, 0, 0]):
    new = desired_replicas(replicas, waiting)
    note = "" if new == replicas else ("  scale UP (Steps 3-5: new GPU pod, load weights, ready)" if new > replicas else "  scale down")
    print(f"t={tick:2}: waiting {waiting:2} on {replicas} replicas -> {new}{note}")
    replicas = new

✓ Ran with Python 3.12.14.

From scratch

The idea in plain Python, no libraries

A tiny version of the mechanism. The Step comments match the numbered steps above. Save it as a .py file and run python3 file.py: nothing to install.

python3 · standard library only
# A queue-based autoscaler for LLM replicas.
import math

traffic = [4, 6, 12, 20, 20, 18, 8, 4, 2, 2]     # new requests per tick
CAPACITY, STARTUP_TICKS = 4, 2                   # requests per replica per tick; time to become ready
ready, starting, queue = 1, [], 0                # starting = ticks left for each new replica

for t, arriving in enumerate(traffic):
    # Step 4-5: replicas that have loaded their weights and passed readiness start serving
    starting = [s - 1 for s in starting]
    ready += starting.count(0)
    starting = [s for s in starting if s > 0]
    queue = max(0, queue + arriving - ready * CAPACITY)
    # Step 1-2: the autoscaler reads the queue metric (not CPU) and decides
    desired = max(1, math.ceil((queue + arriving) / CAPACITY))
    if desired > ready + len(starting):
        starting += [STARTUP_TICKS] * (desired - ready - len(starting))   # Step 3: may need a new GPU node
    elif desired < ready and queue == 0:
        ready -= 1                                 # scale down slowly, one replica at a time
    print(f"t={t}: arriving {arriving:2}  queue {queue:2}  ready {ready}  starting {len(starting)}")

Watch it in a real system
  • Kubernetes: kubectl get hpa -w shows desired vs current replicas changing as the metric moves; kubectl describe hpa <name> shows why it scaled.
  • kubectl get pods -w during a scale-up shows how long a new replica spends Pending (waiting for a GPU node) and starting (loading weights) before it is Ready.
  • Scale on the serving engine’s queue or KV-cache metric (e.g. with KEDA or a custom-metrics adapter), not on CPU.
