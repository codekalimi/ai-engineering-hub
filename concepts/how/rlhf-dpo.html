How do RLHF and DPO (preference tuning) work?

In one lineBoth learn from comparisons where one answer is preferred over another. RLHF trains a reward model and optimizes against it; DPO trains directly on the preference pairs.

Step by step
  1. For many prompts, two answers are generated and a person (or a strong model) marks which is better.
  2. RLHF: a reward model is trained to predict those preferences.
  3. The language model is then optimized with reinforcement learning to get high reward, with a penalty for drifting too far from the original model.
  4. DPO skips the reward model: it directly increases the probability of preferred answers relative to rejected ones.
Key details
  • DPO is simpler and more stable, so it's widely used; RLHF can be more powerful but is harder to tune.
  • Preference data teaches style, helpfulness and safety, not new knowledge.

Use it

What you'd write at work

Preference tuning with TRL's DPOTrainer on (prompt, chosen, rejected) data. beta controls how far the model may move from where it started.

python
from datasets import load_dataset
from trl import DPOConfig, DPOTrainer

dataset = load_dataset("trl-lib/ultrafeedback_binarized", split="train")   # prompt / chosen / rejected
trainer = DPOTrainer(
    model="Qwen/Qwen2.5-0.5B-Instruct",
    train_dataset=dataset,
    args=DPOConfig(output_dir="qwen-dpo", beta=0.1, learning_rate=5e-7),
)
trainer.train()      # logs rewards/chosen, rewards/rejected and rewards/margins - margins should rise

Checked, not run: needs a GPU and hours of training; syntax and imports were checked.

Under the hood

What the library does for you, with its real classes

The DPO loss computed from a real model's log-probabilities of a chosen and a rejected answer: the same formula DPOTrainer uses.

python
import torch
import torch.nn.functional as F
from transformers import AutoModelForCausalLM, AutoTokenizer

name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
policy = AutoModelForCausalLM.from_pretrained(name).eval()

def answer_logprob(model, prompt, answer):                     # log p(answer | prompt), summed over tokens
    p = tok(prompt, return_tensors="pt").input_ids
    a = tok(answer, add_special_tokens=False, return_tensors="pt").input_ids
    with torch.no_grad():
        logits = model(torch.cat([p, a], dim=1)).logits[0, p.shape[1] - 1:-1].float()
    return logits.log_softmax(-1).gather(1, a[0][:, None]).sum()

prompt = "Q: How do I reset my password?\nA:"
chosen = " Open Settings, choose Security, then Reset password."       # Step 1: preferred
rejected = " Passwords are important for security."                     # Step 1: not preferred
pc, pr = answer_logprob(policy, prompt, chosen), answer_logprob(policy, prompt, rejected)
print(f"log p(chosen) {pc:.1f}, log p(rejected) {pr:.1f}")

beta = 0.1
ref_c, ref_r = pc.clone(), pr.clone()             # at the start, the reference model IS the policy
for shift in (0.0, 2.0, 5.0):                      # pretend training moved chosen up and rejected down
    margin = beta * ((pc + shift - ref_c) - (pr - shift - ref_r))
    loss = -F.logsigmoid(margin)                   # Step 4: the DPO loss
    print(f"after shifting by {shift}: margin {margin:.2f}, loss {loss:.3f}")

✓ Ran with torch 2.15.0, transformers 5.24.0.

What it printed
log p(chosen) -30.0, log p(rejected) -17.6
after shifting by 0.0: margin 0.00, loss 0.693
after shifting by 2.0: margin 0.40, loss 0.513
after shifting by 5.0: margin 1.00, loss 0.313

From scratch

The idea in plain Python, no libraries

A tiny version of the mechanism. The Step comments match the numbered steps above. Save it as a .py file and run python3 file.py: nothing to install.

python3 · standard library only
import math

# Step 1: one preference pair - same prompt, a chosen (better) and a rejected answer.
# Numbers are log-probabilities of each whole answer under each model.
policy = {"chosen": -12.0, "rejected": -11.0}       # the model being trained prefers the WRONG one
reference = {"chosen": -12.0, "rejected": -11.0}    # frozen copy of the starting model
beta, lr = 0.1, 5.0
sigmoid = lambda z: 1 / (1 + math.exp(-z))

# Step 4 (DPO): raise chosen relative to the reference, lower rejected - no reward model needed
for step in range(1, 6):
    margin = beta * ((policy["chosen"] - reference["chosen"]) - (policy["rejected"] - reference["rejected"]))
    loss = -math.log(sigmoid(margin))
    push = lr * beta * (1 - sigmoid(margin))            # size of the gradient step
    policy["chosen"] += push
    policy["rejected"] -= push
    print(f"step {step}: margin {margin:+.3f}  loss {loss:.3f}  "
          f"logp chosen {policy['chosen']:.2f}  rejected {policy['rejected']:.2f}")

# Step 2-3 (RLHF) instead trains a reward model on such pairs and runs RL (e.g. PPO) against it,
# with a KL penalty that keeps the model near the reference - the role beta plays here.

✓ Ran with plain Python 3.9+.

Watch it in a real system
  • TRL DPOTrainer logs rewards/chosen, rewards/rejected and rewards/margins: the margin should grow during training, like below.
  • Look at a preference dataset on the Hugging Face Hub (columns prompt, chosen, rejected) to see what the training signal actually is.
