Mental Templates

scikit-learn has import → fit → predict. LangChain has a template just as small. Learn it once, then plug in add-ons as the problem needs them.

The one to memorize

The core template

Every LangChain program follows these five steps. There's no fit, because the model is already trained. Writing the prompt does that job instead.

  1. 1Importthe parts you need
  2. 2Modelchoose the LLMChatAnthropic(...)
  3. 3Promptinstructions with {placeholders}ChatPromptTemplate
  4. 4Chainconnect the partsprompt | model | parser
  5. 5Invokerun it with real valueschain.invoke({...})
# 1. IMPORT
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 2. MODEL
model = ChatAnthropic(model="claude-sonnet-5-5")

# 3. PROMPT
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a {role}."),
    ("user", "{question}"),
])

# 4. CHAIN
chain = prompt | model | StrOutputParser()

# 5. INVOKE
print(chain.invoke({"role": "math tutor", "question": "What is 2+2?"}))
Remember

Everything else in LangChain is this block with one or two extra parts plugged in.

Variation A

RAG template: answer from my documents

Two phases. Indexing runs once; asking runs on every question and is the core template with a retriever in front.

Index · onceLoad→Split→Embed→Store
Ask · alwaysRetrieve→Prompt→Model→Answer
# INDEX
docs      = PyPDFLoader("policy.pdf").load()                                   # Load
chunks    = RecursiveCharacterTextSplitter(chunk_size=1000).split_documents(docs)  # Split
store     = Chroma.from_documents(chunks, embeddings)                          # Embed + Store
retriever = store.as_retriever()

# ASK: the same 5-step skeleton, with a retriever in front
prompt = ChatPromptTemplate.from_template(
    "Answer using this context:\n{context}\n\nQuestion: {question}")
chain = {"context": retriever, "question": RunnablePassthrough()} | prompt | model | StrOutputParser()
chain.invoke("Can I get a refund?")

Variation B

Agent template: let it use tools

Write tools as plain functions with a clear docstring, hand them to create_agent, and run it. The tool-calling loop is built for you.

Tools→Model→create_agent→invoke
@tool
def get_weather(city: str) -> str:
    """Get the current weather for a city."""
    ...

agent = create_agent(model, tools=[get_weather], system_prompt="You are helpful.")
agent.invoke({"messages": [("user", "Weather in Paris?")]})

Variation C

LangGraph template: my own workflow

LangGraph has its own five steps. Remember them as S-N-E-C-R: State, Nodes, Edges, Compile, Run.

  1. SStatewhat the graph remembersclass MyState(TypedDict)
  2. NNodesfunctions that do the workdef node(state): return {...}
  3. EEdgesarrows between nodesadd_conditional_edges
  4. CCompilebuild it, add memorygraph.compile(checkpointer=...)
  5. RRuninvoke with a thread_idapp.invoke(input, config)
class State(TypedDict):                              # 1. STATE
    messages: Annotated[list, add_messages]

def chatbot(state: State):                           # 2. NODES
    return {"messages": [model.invoke(state["messages"])]}

graph = StateGraph(State)
graph.add_node("chatbot", chatbot)
graph.add_edge(START, "chatbot")                     # 3. EDGES
graph.add_edge("chatbot", END)

app = graph.compile(checkpointer=InMemorySaver())    # 4. COMPILE

app.invoke({"messages": [("user", "Hi!")]},          # 5. RUN
           {"configurable": {"thread_id": "1"}})

Map it to what you know

Next to scikit-learn and an API controller

Pipeline in scikit-learn and | in LangChain are the same idea: steps joined so each output feeds the next. And just as every scikit-learn model has fit and predict, every LangChain part has invoke, batch and stream.

An API controller is even closer to LangGraph: the request shape is the state, the helper functions are the nodes, and the order of calls plus the if/else are the edges.

Same logic, two ways

Placing an order: look up the user, check stock, charge the card, return the result. The numbers in the comments show which part matches which.

API controller (what you already write) 
# ① import
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from services import get_user, check_stock, charge_card

# ② the data shape
class OrderRequest(BaseModel):
    user_id: int
    item_id: int

app = FastAPI()                            # ⑤ build the app

@app.post("/orders")                       # ⑤ register the route
def create_order(req: OrderRequest):
    user = get_user(req.user_id)           # ③ call a function
    if not check_stock(req.item_id):       # ④ logic: branch
        raise HTTPException(409, "Out of stock")
    payment = charge_card(user, req.item_id)   # ③ call another
    return {"status": "ok",                # ⑥ return
            "payment_id": payment.id}
Same thing as a LangGraph 
# ① import
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# ② the data shape = state
class OrderState(TypedDict):
    user_id: int
    item_id: int
    in_stock: bool
    payment_id: str

# ③ each helper call becomes a node
def check(state):
    return {"in_stock": check_stock(state["item_id"])}

def charge(state):
    user = get_user(state["user_id"])
    return {"payment_id": charge_card(user, state["item_id"]).id}

graph = StateGraph(OrderState)
graph.add_node("check", check)
graph.add_node("charge", charge)
graph.add_edge(START, "check")
graph.add_conditional_edges("check",       # ④ the if/else
    lambda s: "charge" if s["in_stock"] else END)
graph.add_edge("charge", END)

app = graph.compile()                      # ⑤ build it
app.invoke({"user_id": 7, "item_id": 42})  # ⑥ run → final state

For plain business logic like this, keep the controller: it's simpler. LangGraph is worth it when a step is an LLM making a decision, when the flow loops, or when it must pause for a human and resume later.

Where LangChain sits in a real API

In practice you don't replace the controller. The chain or graph is one more function the controller calls, like get_user.

@app.post("/ask")
async def ask(req: AskRequest):
    user = get_user(req.user_id)                        # normal helper
    if not user.is_active:                              # normal logic
        raise HTTPException(403, "Inactive account")

    answer = await chain.ainvoke({                      # ← LangChain is just another call
        "question": req.question,
        "plan": user.plan,
    })
    save_to_history(user.id, req.question, answer)      # normal helper
    return {"answer": answer}                           # normal return
Before you write code

10-second recall

CHAIN:     Model → Prompt → Chain → Invoke
  + data?    put a Retriever before the prompt      (RAG)
  + actions? give the model Tools                   (Agent)
  + memory?  keep messages / use a thread_id
  + control? wrap it in a graph: State → Nodes → Edges → Compile → Run

Facing a new problem, ask these four questions in order. The answers tell you which template to use.

  1. 1
    What does the model need to know?Write the prompt. If the answer is in your documents, add a retriever.
  2. 2
    What does it need to do?If it must act or look things up, add tools.
  3. 3
    What should it remember?For a conversation, add memory: message history or a checkpointer.
  4. 4
    Straight line, or does it loop or wait?Straight: a chain. Loops, retries or human approval: LangGraph.
